# fixtures/ — complete guides, kept in-repo as test subjects

This folder holds **finished GuideForge guides**, generated by the pipeline and kept here on purpose. They are
not examples to show off and not advice to follow: they are the things the repo's checks get to run
**against**.

| | |
|---|---|
| [idempotent-api-dotnet/](idempotent-api-dotnet/) | An idempotent Minimal API in .NET 10 — 5 milestones, 19 steps, 5 verify gates, 38 files. Generated with `v1.14.1` from a plan produced by `plan-guide`; maintained since with `audit-guide` + `report-issue`, whose findings are in its drift log. |
| [color-picker-component-angular/](color-picker-component-angular/) | An Angular colour picker shipped as a plain HTML custom element — 5 milestones, 23 steps, 5 verify gates. Generated with `v1.15.0`. Its gates are the opposite kind: no test runner exists in the guide at all, so every one of them is a person reading exact values off a static demo page. |
| [color-picker-component-react/](color-picker-component-react/) | **The same picker, on React 19 + Vite 8** — 5 milestones, 23 steps, 5 verify gates. Generated with `v1.15.0`. Same product, same end state, same canonical colour, same human gates: the only variable is the stack. |

**The name is `<what it builds>-<technology>`, in that order, on purpose.** What it builds comes first because
that is what distinguishes one fixture from the next — a second guide on the same stack should sit apart from
the first in a directory listing, not blur into it. The technology comes last because it is the part a reader
scans for. The two colour pickers are exactly the case that naming was built for.

The stacks were not chosen for their own sake. The first two sit at opposite ends of the axis that decides
whether a guide can ever be checked without a human: every gate in the .NET guide is `dotnet test` with an exit
code, which makes it the first guide here a machine could eventually verify end to end; every gate in the
Angular guide is a person looking at a browser, which is the harder case the contract has to survive too.

**The third is a controlled pair with the second**, and that is its whole reason for existing. Same brief, same
observable end state, same `#3366ff`, same browser-watched gates — so the *only* thing that differs is the
stack, and any difference in the two guides is attributable to it rather than to taste. What the pair actually
shows is that the build-vs-borrow table inverts on one row: Angular's element bridge is `@angular/elements`, an
in-house package versioned with the framework, so the row is **borrow** and it is not close; React has no
equivalent, so writing the bridge by hand is the React guide's spine and its widest milestone. One capability,
plumbing in one guide and the subject of the other.

## Why guides live here when guides are never vendored

[examples/real-examples.md](../examples/real-examples.md) links guides in **their own repositories**, because
this repo ships the method and the output belongs to whoever generated it. That rule is about *output*. This
folder holds *fixtures*: known-good artifacts that exist so the contract can be checked against something
real, in-tree, without cloning anything.

The distinction that matters: **an example is evidence, a fixture is a test subject.** Nothing here is offered
as proof that the method works, and nothing here should be linked as a showcase.

## What they are for

- **A target for the layout contract.** [reference/canonical-layout.md](../reference/canonical-layout.md)
  describes a skeleton in prose; these are that skeleton as files — nav lines at both ends, `00_overview.md`
  maps, one gate per `NN_verify.md`, foundation docs under `foundation/`.
- **A subject for `audit-guide`.** Running the audit over a guide the repo controls makes the audit's own
  findings reproducible: same input, same expected report.
- **A regression target for a future deterministic checker.** A script that validates a generated guide
  mechanically needs something to validate; these are it.
- **A worked reference when changing the contract.** When a rule moves, this is where you can see what the
  change actually does to a finished guide — and, with two stacks here, whether it does the same thing to a
  machine-gated guide and a human-gated one.

## What they are not

- **Not verified.** The .NET guide's code compiles and thirteen of its fourteen tests have been run green on
  SDK 10.0.302 — audits built the end state from the checkpoints, and one execution run typed all 19 steps in
  order, which is what caught its three broken break recipes; the fourteenth test was added by that fix and
  has never been run. But **nobody has followed either guide as written, in order, as a reader**,
  which is the only thing that verifies a milestone. Every milestone in both sits below ✅. Each guide's own
  `foundation/status.md` is the authority; the drift log there records what each audit found.
- **Not templates.** Copying one would copy one plan's answers — one audience matrix, one stack, one ladder.
  Generate your own.
- **Not maintained against upstream releases.** Both are pinned to the stack verified on the day they were
  drafted, and they should stay pinned: a fixture that drifts stops being a fixture.
